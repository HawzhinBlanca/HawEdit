### DELIVERABLE 3 — the agent architecture (resolving Report A vs Report B)

**Decision: Pydantic AI (single agent) + DBOS, on the Threadripper box, with the read-only constraint enforced below the agent at the OS and database layers. Not Claude Agent SDK + Temporal.**

Reasoning:
- **Single agent, not multi-agent.** Both verified arXiv papers (2604.02460 and 2606.13003) point the same way: at equal compute, a single well-orchestrated agent matches or beats orchestrated multi-agent systems, and automatic MAS is mostly bloat. HawEdit's pipeline is a deterministic DAG with one reasoning judge — it does not need an agent swarm.
- **Pydantic AI over Claude Agent SDK** because HawEdit's data contracts are typed and Pydantic is already the validation layer; typed tools/structured outputs are native; and it is model-portable (you can route the judge to Gemini/Vertex, which you must).
- **DBOS over Temporal** because this is a single Windows/Threadripper box. DBOS adds durable workflows with only a Postgres dependency — no orchestration server to run. Temporal's replay model is worth it only at multi-host/HA/cross-region scale, which HawEdit is not. Caveat from Deliverable 1 #4: decompose long renders into durable steps so crash recovery is meaningful.

**Where the read-only constraint lives (the core technical answer):**
The rule "the agent must never mutate the app" must be enforced where the agent's *identity* structurally lacks the capability to write — never in agent hooks or even solely in Pydantic AI tool handlers (those are application-layer and bypassable by any code path the model can reach). Layered, defense-in-depth:

1. **PostgreSQL read-only role (hard, engine-enforced, OS-independent).** Give the agent a dedicated login role: `GRANT SELECT` only, `NOSUPERUSER`, non-owner, with `ALTER DEFAULT PRIVILEGES ... GRANT SELECT` and `REVOKE CREATE ON SCHEMA public FROM PUBLIC`. The agent's DB identity then physically cannot INSERT/UPDATE/DELETE regardless of the SQL it emits (PostgreSQL GRANT/REVOKE docs). Note: an object *owner* or superuser always retains write access regardless of REVOKE, so the agent role must be a plain non-owner.
2. **Filesystem isolation via WSL2 Linux container with `:ro` bind mounts** — which HawEdit already uses for OmniASR. Mount code/data read-only (`-v HOST:CONTAINER:ro`), `--read-only` rootfs, writable `tmpfs`/named volume only for outputs. Inside that Linux container you additionally get seccomp/AppArmor. GPU passthrough: install only the NVIDIA Windows driver (never a Linux GPU driver inside WSL2 — it would overwrite the projected `libcuda.so` stub), use `--gpus all`; RTX 3090 Ti in WDDM mode is supported (NVIDIA CUDA-on-WSL guide; note NVIDIA lists datacenter GPUs as unsupported for WSL passthrough — consumer RTX is fine).
3. **If running Python directly on Windows instead:** a dedicated low-privilege Windows account with NTFS ACLs granting only Read & Execute to app/data directories. Windows **Job Objects govern CPU/memory/process-lifetime only — they do NOT restrict filesystem writes** (their security-limit feature was removed after Windows XP/Server 2003), so use them only to cap/kill runaway multi-hour jobs. AppContainer is a real kernel security boundary but requires a custom LowBox-token launcher for an unpackaged `python.exe` — not a config flag, contrary to some blog claims.
4. **seccomp/AppArmor are Linux-only** — they do nothing for a native `python.exe` on the Windows host (Docker Desktop on Windows reports the seccomp profile as effectively unconfined); they apply only inside WSL2/Linux containers.

**Observability:** keep it lean — Pydantic AI emits OpenTelemetry spans natively (works with Logfire); DBOS emits OTel spans per workflow/step. That covers what Langfuse would, without another service. For lineage, emit OpenLineage-format events from the artifact ledger rather than deploying Marquez.

### DELIVERABLE 2 — what takes HawEdit to #1 (decided, not optioned)

**The differentiator is Sorani editorial correctness, enforced by machine-checkable invariants and provenance — not the agent stack. Build the Sorani editorial benchmark and make the invariants the product.**

**A. Competitive frontier (Aug 2026).** Opus Clip leads on multimodal moment-finding ("ClipAnything" analyzing speech+visual+sound+emotion) with a 0–100 Virality Score and a *marketed* ~90% highlight-selection accuracy; Vizard optimizes for volume and language reach (subtitles in 100+ languages, dubbing in 29), cleaner cuts, and cheaper per-minute throughput. Descript owns transcript-based editing; Captions/Submagic own caption aesthetics. **Measured failure modes** — the gap between marketing and independent tests is the whole story: reap.video's "State of Top AI Video Clipping Tools 2026" measured "60-70% clip-selection accuracy on solo-speaker content dropping to ~40% on multi-speaker conversations," with "roughly 70% of generated clips need manual cleanup." On captions, ScaleReach's 30-day 2026 test found "~88% on conversation with overlap or non-American accents" versus the 97% marketing claim, so interviews/panels "expect a manual review pass per clip"; AI Tool Radar similarly reports Opus non-English caption accuracy at "approximately 90-92%...for German and Spanish content, with errors most common on technical terms and proper nouns." **Quality bar HawEdit must clear:** complete-sentence boundaries (no mid-sentence cuts), correct Arabic-script RTL complex shaping, and dialect awareness. No global tool demonstrably handles Sorani editorial quality or RTL complex shaping correctly — Vizard's "100+ languages" is untested on Central Kurdish editorial judgment and complex-shaping burn-in, and every measured tool degrades hardest on exactly the multi-speaker, non-English, overlap-heavy footage that Kurdish media produces.

**B. Where the moat is — Sorani specialization is a genuine moat.** Central Kurdish/Sorani is spoken by 7–9 million people (Indiana University CEUS: "Sorani is spoken by 7 to 9 million people, mostly in northern Iraq and western and northwestern Iran"; Ethnologue lists ~6.8M), is Arabic-script and RTL, is one of Iraq's two official languages (with Arabic), and spans a dialect continuum (Hewlêr/Slemani/Mukriyan). No major repurposing product treats it as a first-class editorial language. The moat is threefold and compounding: (1) linguistic correctness (KLPT normalization, complex shaping via libass/HarfBuzz/FriBidi, dialect handling); (2) the machine-checkable editorial invariants that structurally prevent the exact defects competitors ship; (3) local-first privacy as a product feature for politically sensitive Kurdish media (Kurdish outlets are partisan and press-freedom-constrained, so on-prem processing of client footage is a selling point, not just a compliance checkbox). The same pipeline extends to adjacent low-resource/RTL languages (Kurmanji, Southern Kurdish, other MENA languages) — the pipeline is the reusable asset.

**C. Good clipper vs creative director.** Genuinely achievable today: query-conditioned moment retrieval and saliency scoring (QVHighlights, TVSum, YouTube Highlights are the academic bases; long-form is under-served — SVHighlights at KDD 2026 targets extremely long video), and cross-modal salience fusing speech + visual + audio (Opus's ClipAnything is the shipped proof). Aspirational/oversold: true causal "why this moment works" emotional-beat reasoning — LLMs generate plausible rationales but there is no validated ground truth, so treat those as *explanations for editor trust*, not proof of quality. HawEdit's dual-path discovery (full-transcript verbal path UNION VideoChat3 visual path) feeding a KURDISH_EDITORIAL_JUDGE is a legitimate creative-director architecture — but only once the judge is validated against human Sorani reviewers.

**D. Editorial quality evaluation.** Measure auto-clip quality with: Recall@K and temporal IoU against human-selected moments (HawEdit's `repurposing.py` already targets these), a misleading-edit rate (does the clip misrepresent the source?), and blind human-preference win-rate. For Sorani, where no benchmark exists, HawEdit's dialect-balanced two-reviewer manifest IS the contribution — publishing/owning it is itself a durable asset competitors cannot cheaply replicate.

**F. "Self-improving through use," honestly.** What works: preference accumulation (bounded — AWS's ~1,000-pair floor and arXiv 2603.20100's low-data collapse mean don't expect DPO magic at small scale); learned/calibrated critics with evidence-gated promotion (HawEdit's `judge.py` "promotion only on evidence" is exactly right); eval-driven refinement; memory/exemplar systems. What's marketing: "learns from every edit" auto-improvement. **Buildable design at realistic scale:** log every editor accept/reject/adjust decision plus reviewer scores as preference pairs; use them first as few-shot exemplars and judge-calibration and as the gate on any prompt/model change (shadow eval against the benchmark); only move to actual DPO/KTO fine-tuning once you cross ~1,000+ quality pairs. This improves editorial quality from real usage without over-promising.

**G. Non-obvious ideas — and HawEdit already holds the best ones.** The highest-leverage differentiators are: (1) **machine-checkable invariants as the verifier/critic** for every editorial proposal — this is HawEdit's single biggest edge and directly kills the competitors' top failure mode; (2) **provenance-backed "why this cut"** (HawEdit's `delivery.py` already emits an EDL on the source timeline with anchor provenance) — editor trust as a feature; (3) **pipeline artifacts + lineage as the agent's world model** (emit OpenLineage events); (4) **editorial conventions as portable SKILL.md skills**; (5) **active learning that asks the human the single highest-information question**; (6) **local-first privacy** as above. The strategic insight: HawEdit's rigor culture — the hard gate, the invariants, the provenance, "unmeasured is None," "a number carries its provenance or it is not a number" — is not scaffolding for the product; it IS the moat.
